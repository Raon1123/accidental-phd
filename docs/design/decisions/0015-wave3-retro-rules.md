## 결정
1. **감사 '변경' 판정의 반영 주체는 초안 역할이다.** 판정자는 스펙과 결정 기록 본문을 직접 고치지 않는다. 판정 표의 이유 칸에 새 값, 계산식, 입력 레코드 id, 0014 "쓰이는 곳" 열의 위치를 전부 적는다. 초안 역할이 그 위치를 모두 고친 뒤, 판정자는 옛 값을 저장소 전체에서 검색해 남은 위치가 0건임을 PR 본문에 적는다. 회고·감사 파일처럼 옛 값을 이력으로 인용하는 파일은 검색에서 빼되, 뺀 파일 목록을 같은 줄에 적는다.
2. **판정 뒤 데이터 수정은 repo 도구로 하고 검사 출력을 PR 본문에 붙인다.** 판정을 데이터에 반영하는 스크립트는 `scripts/`에 커밋하고, markdown 표는 `scripts/md-table.mjs`로 절 제목을 지정해 읽는다. 쓰기 전에 읽은 건수가 기대 건수와 다르면 아무것도 쓰지 않고 멈춘다. 바꾼 레코드마다 바꾸려던 마커 밖에서 사라진 문장 수를 `scripts/compare-notes.mjs` 방식으로 출력하며, 그 수는 0이어야 한다. 이 출력을 PR 본문에 그대로 붙인다.
3. **감사 대상에 감사자 자신의 작업이 있으면 감사자를 바꾼다.** 감사 대상에 감사자가 같은 wave에서 한 판정이나 데이터 수정이 들어 있으면, 그 작업의 대화 맥락이 없는 새 세션 또는 다른 모델이 감사한다. ChatGPT 경로로 감사하면 Astra를 쓴다. wave 파일의 모델·effort 표에는 "스펙 감사" 행을 "판정" 행과 분리해 적는다. 감사 파일 머리에 감사자의 세션·모델을 적어 이 조건을 확인할 수 있게 한다.
4. **보정으로 바꾼 assumed 값은 0014 해당 행을 고쳐 남긴다.** Wave 4 보정 모의실험으로 바꾼 값은 새 결정 기록을 쓰지 않고 0014 해당 행의 값을 고친다. 그 행 끝에 "보정 YYYY-MM-DD, 결과표 링크"를 적고, "쓰이는 곳" 위치 전파와 옛 값 검색은 결정 (1)을 따른다. 보정 결과표 `docs/oracle/calibration-wave4.md`는 Wave 4 종료 조건에 들어간다. 허용 범위(0014 #52) 밖으로 남은 목표는 결과표에 원인 후보를 적고, 같은 내용을 Wave 6 이월 목록([wave-06](../../waves/wave-06-balance-retro.md) 체크리스트)에 옮긴다.
5. **결정 기록 승인은 상태 줄에 PR 번호로 남긴다.** PR 머지로 승인된 결정 기록은 상태 줄을 "승인됨 · 날짜 (PR #N 머지, 0010 §3 (b))"로 바꾼다. 머지된 PR 안에서는 이 줄을 바꿀 수 없으므로, 머지 뒤 첫 PR(보통 다음 wave의 첫 PR)에서 바꾼다. 채팅으로 받은 승인은 PR 댓글로 옮겨 적었을 때만 0010 §3 (a)로 인정하고, 상태 줄에 그 댓글 링크를 적는다. 회고의 "결정 기록으로 올릴 것" 후보는 다음 wave의 첫 PR에서 "제안됨" 상태의 결정 기록으로 만들고, 만들지 않은 후보는 그 사유를 다음 회고에 적는다. Wave 2 회고 후보 8건 중 "리뷰 없는 머지와 결정 기록 승인"은 이 결정이 다루고, 나머지 7건은 Wave 4 회고가 결정 기록으로 만들지 판정해 사유를 적는다.

### 반대 근거
- (1) 반영을 초안 역할에게 돌려보내면 감사 한 번에 넘겨주기가 한 번 늘고, 판정자가 직접 고칠 때보다 감사가 늦게 끝난다. 그래도 Wave 3에서 판정자가 직접 고친 네 항목 모두에 결함이 남았다(#58·#59 값 오류, #87·#104 전파 누락). 넘겨주기를 두면 판정 표의 이유 칸이 반영 지시서가 되어야 하므로 위치와 계산식이 빠지지 않는다. 이 이유로 속도를 포기한다.
- (2) 검사를 `npm run validate` 같은 검증기가 강제하면 PR 본문 출력보다 확실하다. 그러나 치환마다 마커와 기대 건수가 달라 일반 규칙으로 쓰기 어렵고, 검증기는 이미 쓴 결과만 보므로 쓰기 전에 멈출 수 없다. 그래서 스크립트 수준 검사와 PR 본문 출력으로 정한다.
- (3) 감사마다 새 맥락을 열면 근거 색인과 스펙을 다시 읽는 비용이 들고, 다른 모델은 프로젝트 규약을 덜 안다. 그러나 Wave 3 감사가 놓친 결함은 모두 감사자 자신의 작업에서 나왔다. 이 규칙은 감사 대상에 감사자의 작업이 있을 때만 적용하므로 비용은 그 경우로 한정된다.
- (4) 보정 변경마다 새 결정 기록을 쓰면 변경 이력이 결정 기록 목록에 바로 보인다. 그러나 한 번의 보정에서 여러 항목이 함께 바뀌므로 값이 여러 파일에 흩어지고, 0014의 값과 "쓰이는 곳" 열이 서로 다른 파일에 있게 된다. 이력은 git과 행 끝의 날짜·결과표 링크로 추적한다.
- (5) 머지를 승인으로 보면 리뷰 없는 머지가 곧 승인이 된다(Wave 2 PR 13건, Wave 3 PR #36 전 상태 줄). 다음 wave 첫 PR에서 후보를 결정 기록으로 만들라는 규칙은 그 PR을 키운다. 그래도 승인 근거가 repo 안에 남고 회고 후보가 사라지지 않는 쪽을 택한다. 리뷰 없는 머지 자체를 막을지는 Wave 2 후보로 남아 있으며 이 결정의 범위가 아니다.

## 결과
얻는 것: 감사 변경이 "쓰이는 곳" 위치 전부에 반영되었는지를 옛 값 검색 결과로 확인한다. 데이터 치환의 과잉 매칭은 쓰기 전에, 문장 손실은 PR 본문에서 드러난다. 감사자가 자기 작업을 감사하지 않는다. assumed 값의 현재 값과 보정 이력이 0014 한 파일에 모인다. 결정 기록 승인 근거와 회고 후보의 처리 결과가 repo 안에 남는다.

잃는 것: 감사 한 번에 넘겨주기 한 번과 새 맥락을 여는 비용이 더해진다. 다음 wave의 첫 PR이 커진다. 0014 행이 보정 이력만큼 길어진다.

다시 볼 조건: Wave 4 회고에서 넘겨주기 때문에 감사가 wave 안에 끝나지 않았을 때, 옛 값 검색에서 뺀 파일 목록이 이력 파일 밖으로 늘어날 때, 같은 종류의 데이터 치환이 두 번 이상 반복될 때(검증기 강제를 다시 검토), 보정으로 바뀐 0014 행이 많아 행 끝 이력 때문에 표를 읽기 어려울 때.
