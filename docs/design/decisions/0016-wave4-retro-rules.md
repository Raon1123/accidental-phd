# 0016. Wave 4 회고 반영: 묶음 PR 병합 방식, 스펙과 구현이 다를 때의 정본, 보정에서 자동 정책의 지위

## 상태
승인됨 · 2026-10-14 (PR #64 머지로 승인, 결정 기록 0010 §3 (b); Wave 4 회고 §결정 기록으로 올릴 것 3건; 판정자 fable, Wave 4 구현·리뷰 맥락 없는 별도 agent, 결정 기록 0015 §3)

## 맥락
약어는 [용어집](../../workflow.md#용어집)을 따른다. PR은 pull request(브랜치 병합 요청), UI는 user interface(화면), squash 병합은 PR의 커밋 전부를 커밋 하나로 합쳐 main에 넣는 방식, 병합 커밋(merge commit)은 PR의 커밋을 그대로 두고 부모가 둘인 커밋으로 잇는 방식이다. 스펙 세 편은 Wave 3 회고와 같이 상태 스펙, 선택권 스펙, 노동 스펙이라 부른다. 이 기록은 [Wave 4 회고](../../waves/wave-04-engine-impl.md) §결정 기록으로 올릴 것 3건을 하나씩 결정으로 바꾼다. 형식은 결정 기록 0010·0015를 따른다.

1. **묶음 PR의 병합 방식.** `docs/workflow.md` §브랜치·PR 규약은 "머지는 squash"다. 그러나 main의 병합 이력 25건은 전부 병합 커밋이고(`git log --first-parent --no-merges`는 최초 커밋 하나만 남는다), 머지된 PR 18건 중 squash는 0건이다. Wave 4 체크리스트는 완료 근거로 PR 안의 커밋 해시(698813d, 4ef77dc, fa71273, 9ccef67, 02909c1, e725061, 78d80bf, 8f29487, 95de056)를 인용하고, 결정 기록 0015도 72ad355·f6e713f·349c317·d00ba5c를 인용한다. squash였다면 이 해시는 main에서 도달할 수 없다. Wave 2 회고도 같은 쟁점("병렬 PR의 머지 방식과 STATUS 갱신 시점", 13건 모두 병합 커밋)을 후보로 올렸고 결정 기록이 되지 않았다. 0015 §5는 Wave 2 후보의 처리를 Wave 4 회고에 맡겼다. 저장소 설정은 squash·merge·rebase 세 방식을 모두 허용한다.
2. **스펙과 구현이 다를 때의 정본.** Wave 4 엔진이 스펙과 다르게 한 곳은 `engine/src/phd/tick.ts` 머리 주석 (a)~(e)와 PR #49 본문 "스펙 대비 단순화", `engine/README.md` §4에만 적혀 있고 스펙 본문은 옛 서술 그대로다(예: 선택권 §3.4 "결정한 달부터", 엔진은 다음 달부터). [차이 감사](../../superpowers/specs/2026-10-14-wave4-divergence-audit.md)가 14행을 판정해 스펙을 고침 10, 구현을 고침 2, 차이 유지 2로 나눴다. issue #55(UI 결정 지점 화면)와 Wave 6 밸런스가 어느 문서를 기준으로 읽을지 정해야 한다.
3. **보정에서 자동 정책의 지위.** Wave 4 보정(`docs/oracle/calibration-wave4.md` §원인 후보)은 0014 #45(M̄ 0.68 → 0.40)와 #46(자격시험 합격 후 포커스 가중치 0.5/0.2/0.2/0.1 → 0.3/0.1/0.5/0.1)을 한 쌍으로 바꿨다. 사유는 "자동 정책은 합격 전에 쓸 초고가 없어 `write`를 고르지 않는다"였다. 선택권 §4.4의 문구("활성 초고가 있고 writing < 100 → write")가 그 구조를 만든다: 초고는 집필 포커스만 만들고, 집필은 초고가 있어야 고르므로 자동 정책은 첫 초고를 시작할 수 없다. 보정 목표(선택권 §4.6, 노동 §4.3)의 기준값은 재적 학생·학위 취득자 전체의 통계(레코드)이고, 사람 플레이어의 포커스·결정 분포 레코드는 없다(0014 #46 사유). 동기 4명은 플레이어와 같은 정책을 쓴다(상태 §6.4, 선택권 §4.4).

## 결정
1. **PR은 병합 커밋으로 머지한다. squash·rebase 병합은 쓰지 않는다.** 묶음 PR(결정 기록 0010 §1)과 단일 issue PR을 가리지 않는다. 이유는 wave 체크리스트·결정 기록·보정 결과표가 완료 근거와 옛 값 검색 기준(0015 §1·§2)으로 PR 안의 커밋 해시를 인용하기 때문이다. `docs/workflow.md` §브랜치·PR 규약의 "머지는 squash." 문장을 병합 커밋 규칙으로 바꾼다(바꿀 문장은 차이 감사 §3.4). STATUS 갱신 시점은 바꾸지 않는다(같은 PR 안에서 갱신). 저장소 설정에서 squash·rebase를 끄는 것은 관리자가 한다. 이 결정으로 Wave 2 후보 "병렬 PR의 머지 방식과 STATUS 갱신 시점"은 닫힌다.
2. **스펙이 정본이다. 구현이 스펙과 다르면 차이는 임시이며, 다음 wave 첫 PR의 행 단위 감사로 스펙 또는 구현 중 하나를 고쳐 차이를 없앤다.** 절차: (a) 구현 PR은 스펙과 다르게 한 곳을 PR 본문과 해당 함수 주석에 적는다. 이 목록은 머지 뒤 다음 wave 첫 PR까지만 유효한 임시 목록이다. (b) 다음 wave 첫 PR에서 구현에 참여하지 않은 판정자(0015 §3)가 `docs/prompts/judge-any.md` §과제 4의 표(스펙 절, 구현 위치, 결과가 달라지는 입력 예, 판정)를 `docs/superpowers/specs/<날짜>-<wave>-divergence-audit.md`에 쓴다. (c) 초안 역할이 "스펙을 고침" 행은 스펙 본문과 0014 "쓰이는 곳" 위치에, "구현을 고침" 행은 코드와 테스트에 반영한다(0015 §1 절차, 옛 문장 검색 0건을 PR 본문에). "차이 유지" 행은 스펙과 코드가 같은 뜻이라는 판정이므로 README·주석의 "단순화" 표현을 스펙 절 인용으로 바꾼다. (d) 반영이 끝나면 `engine/README.md`와 코드 주석에는 차이 서술이 남지 않고 스펙 절 인용만 남는다. (e) 반영 전까지 UI(issue #55)와 밸런스(Wave 6)는 스펙 위에 감사 표의 판정 열을 겹쳐 읽는다. 즉 "스펙을 고침" 행은 감사 표의 바꿀 문장이, "구현을 고침" 행은 스펙 원문이 기준이다. Wave 4 차이 14행의 반영은 issue #51의 남은 일이다.
3. **보정 목표는 자동 정책(동기 정책)으로 잰다. 단, 정책 가중치는 보정 손잡이가 아니다.** (a) 선택권 §4.2가 M̄를 "자동 진행 정책에서 g 외 배수들의 기댓값"으로 정의하고, 동기 4명이 같은 정책을 쓰므로(상태 §6.4) 보정 모의실험의 측정 대상은 자동 정책이다. 사람 행동 모형은 두지 않는다. (b) 선택권 §4.4의 정책 문턱·가중치(0014 #46)는 보정에서 바꾸지 않는다. 보정은 환경 상수(진척·위험률·자금·노동시장, 0014의 #46 이외 행)만 움직인다. 정책을 바꿔야 목표에 든다고 보이면 보정 결과표에 "정책 변경 후보"로 적고 `needs-judge`로 넘긴다(0015 §4의 0014 행 수정 절차가 아니라 선택권 §4.4 설계 변경 판정이다). (c) 2026-10-14의 #46 변경은 PR #49 머지로 승인된 0014 행이므로 되돌리지 않는다. 다만 그 변경의 사유인 "합격 전 집필 없음"은 선택권 §4.4 문구가 만든 구조이므로, 자동 정책이 첫 초고를 시작하는 규칙(예: 초고가 없을 때 집필을 고를 조건)을 Wave 6 체크리스트에 정책 설계 항목으로 올린다. 새 가중치 값은 이 기록이 정하지 않는다. (d) 보정 결과표는 "정책 고정 + 환경 상수 변경"과 "정책 변경"의 전후를 따로 보고한다.

## 결과
얻는 것: 체크리스트·결정 기록이 인용한 커밋 해시가 main에서 도달 가능하고, 규약과 이력(병합 커밋 25건)이 일치한다. Wave 5 UI와 Wave 6 밸런스가 읽을 문서가 하나(스펙 + 반영 전 감사 표)로 정해진다. 보정 결과가 정책 조정과 환경 조정으로 나뉘어 어느 쪽이 목표를 맞췄는지 읽을 수 있다. 영향 받는 파일: `docs/workflow.md` §브랜치·PR 규약 한 문장; 차이 감사 §3.1의 스펙 절(상태 §2·§7.1·§7.2, 선택권 §2.3·§3.4·§4.2·§9.4, 노동 §4.1)과 0014 #37·#101 값 칸; `engine/src/decide.ts` `reReviewMonths`, `engine/src/career/tick.ts` `advanceYear`와 테스트 2건; `docs/oracle/calibration-wave4.md`의 다음 판 형식. 영향 받는 레코드 id: 없음(레코드 값은 바뀌지 않는다).

잃는 것: main 이력이 PR 커밋 수만큼 길어지고(PR #49는 23건) `git bisect`가 PR 안의 중간 커밋에 멈출 수 있다. 다음 wave 첫 PR이 감사 표와 반영으로 커진다(0015 §5와 같은 방향). 정책을 보정 손잡이에서 빼면 환경 상수만으로 목표에 못 드는 경우가 늘어 `needs-judge`가 잦아진다.

다시 볼 조건: PR 하나의 커밋이 50건을 넘어 이력 읽기가 어려워질 때(그때는 PR 안에서 커밋을 정리하는 규칙을 더한다). 감사 표의 "차이 유지" 행이 wave마다 늘어 스펙이 코드 서술로 변할 때. Wave 6 플레이테스트에서 사람 플레이어의 포커스 구간·결정 선택 분포가 쌓여 자동 정책 분포와 비교할 수 있을 때(상태 §9가 플레이테스트 뒤 재검토를 예고한 항목과 같은 시점).

### 판정 근거
- (1) 출처 근거: main 병합 이력 25건 전부 병합 커밋, `--first-parent --no-merges` 결과 최초 커밋 1건, 머지된 PR 18건에 squash 0건(2026-10-14 `gh pr list --state merged` 확인). Wave 4 체크리스트가 인용한 해시(맥락 1의 9건 외에 c0dca19·380b13e 등)와 0015의 해시 인용 4건은 병합 커밋이라 main에서 도달 가능하다(Wave 4 회고 "체크 메모가 인용한 커밋 해시는 main에서 도달 가능하다"). 0015 §1의 옛 값 검색과 §2의 `scripts/compare-notes.mjs d00ba5c`는 PR 안의 커밋을 기준점으로 쓴다. 설계 가정: 해시 인용을 PR 번호 + 파일 경로 인용으로 바꾸는 쪽보다 이력을 보존하는 쪽이 검사 비용이 적다.
- (2) 출처 근거: 차이 감사 14행 중 10행이 스펙 수정으로 끝났고 그 사유 다수는 스펙 자체의 빈칸(시작 달 필드 없음, 평균 급여 필드 없음, 연장 신청 결정 지점 없음, 등록금 청구 중복)이다. 즉 코드가 틀린 것이 아니라 스펙이 구현 가능한 서술이 아니었다. 그래도 2행(재심 기간 상수, 은퇴 판정 순서)은 스펙이 맞고 코드가 틀렸다. 둘을 가르는 일은 행 단위 판정이 필요하고, 그 결과를 스펙에 되돌려 넣어야 다음 wave가 코드 주석을 뒤지지 않는다. issue #51 본문은 UI(#55)가 이 판정을 따른다고 적었다. 설계 가정: 판정 전 임시 목록을 허용하지 않으면 구현 PR이 스펙 수정까지 떠안아 0015 §3의 독립 감사가 성립하지 않는다.
- (3) 출처 근거: 선택권 §4.2의 M̄ 정의("자동 진행 정책에서 g 외 배수들의 기댓값"), 상태 §6.4(동기는 정책으로 진행), 0014 #46 사유("박사과정생 시간 배분·결정 분포 레코드가 없다"), 보정 결과표 §원인 후보 #46 행("정책만 바꾸고 M̄를 두면 오히려 나빠진다 … #45와 한 쌍"). `engine/src/policy.ts` 15행 주석("스펙 문구 그대로, 초고가 아직 없으면 자격시험 합격 전에는 write를 고르지 않는다")은 합격 전 집필 없음이 코드 결함이 아니라 §4.4 문구의 결과임을 보여준다. 설계 가정: 정책과 환경 상수를 같은 보정에서 함께 돌리면 목표 달성이 정책 조정 때문인지 환경 조정 때문인지 결과표에서 읽을 수 없다. Wave 4 결과표가 바로 그 경우다(#45·#46 쌍).

### 반대 근거
- (1) squash를 지키면 main 이력이 PR 하나당 한 줄이라 읽기 쉽고, 체크리스트는 해시 대신 PR 번호와 파일 경로를 인용하면 된다. 그러나 0015 §1·§2의 검사(옛 값 검색 기준점, `compare-notes.mjs`의 비교 기준 커밋)는 PR 안의 특정 커밋을 가리켜야 하고, 지금까지 18건이 모두 병합 커밋이라 규약을 squash로 유지하면 이력이 두 방식으로 섞인다. 묶음 PR만 병합 커밋으로 하고 단일 PR은 squash로 하는 절충은 PR마다 방식을 판단해야 해서 Wave 2처럼 지켜지지 않을 가능성이 크다. rebase 병합은 해시가 다시 써져 인용이 깨진다.
- (2) 구현을 정본으로 두면(README §4가 행동을 기술) 스펙 수정 비용이 없고 코드와 문서가 어긋날 일이 없다. 그러나 스펙은 레코드 id와 0014 번호로 근거를 다는 유일한 문서이고(상태 §머리 "근거 규칙"), README는 근거를 달지 않는다. 또 "차이 목록이 정본"으로 두면 Wave 5·6이 세 문서(스펙, README, PR 본문)를 함께 읽어야 한다. 임시 목록을 허용하지 않고 구현 PR에서 스펙을 바로 고치게 하는 대안은 0015 §1·§3(판정자가 고치지 않음, 감사자 독립)과 충돌한다.
- (3) 사람 플레이어는 포커스를 바꾸고 확률 힌트를 보며 결정하므로 자동 정책 분포와 다르고, 레코드(휴학률·학위 기간)는 사람 집단의 결과이므로 사람 행동 모형으로 재야 한다는 주장이 가능하다. 그러나 사람 행동 분포 레코드가 없고 플레이테스트 전에는 측정 수단이 없다. 반대로 정책을 보정 손잡이로 계속 쓰면 환경 상수의 검증력이 떨어진다는 것이 Wave 4 결과표의 사례다. #46 변경을 되돌리자는 선택지도 있으나, 그 값은 PR #49 머지로 승인된 0014 행이고(0010 §3 (b)) 되돌리면 학위 기간 중앙값 4/4가 0/4로 돌아간다(결과표 §3).
